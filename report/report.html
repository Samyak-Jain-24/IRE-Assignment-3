Benchmarking Approximate Nearest Neighbour Search: HNSW, IVF-Flat and IVF-PQ

CS4.406 Assignment 3. Everything ran on one laptop: {{num:env_cpu}} ({{num:env_cores_threads}} cores/threads), {{num:env_ram}} RAM, {{num:env_os}}, on AC power. Python {{num:env_python}}, faiss-cpu {{num:env_faiss_cpu}}, numpy {{num:env_numpy}}, h5py {{num:env_h5py}}, threadpoolctl {{num:env_threadpoolctl}}. Every number, table and figure is regenerated by bash run_all.sh; results/results.csv holds all {{num:n_result_rows}} benchmark rows.

Protocol. GloVe vectors and queries are L2-normalised, so L2 distance ranks exactly like angular distance. Queries 0–4999 (tuning half) are used for every choice: where a sweep stops, which configurations form the trade-off curve, and which setting is used for recall 0.90/0.95. Every reported recall and speed comes from queries 5000–9999 (test half). Speed is measured one query per search() call on one thread. Both FAISS's OpenMP threads and its bundled OpenBLAS pthreads, which ignore omp_set_num_threads, are pinned to one thread with threadpoolctl. Each QPS is the median of 3 full passes over the 5000 test queries, each after a warm-up. Builds use all 8 hardware threads. Measuring well on an 8 GB laptop took extra care. Early runs were distorted by Windows paging out the index and by battery-mode throttling (the CPU runs at about half speed on battery). Each script therefore pins its working set (worst timed pass: {{num:faults_per_query_max|.2f}} page faults per query, median {{num:faults_per_query_median|.3f}}) and pauses timing while on battery. A fixed CPU workload timed at the start of every script varied by {{num:cal_spread_pct|.0f}}% across the run, so speed ratios below about 1.3× between numbers measured at different times are within noise. The Python harness costs {{num:call_overhead_us|.1f}} µs per call (measured on a 1-vector index), under 5% of every operating point in Table 2.

1. Exact baseline

recall@10 (our own function, annbench/metrics.py). A returned id counts as correct if its true distance is no larger than the true 10th-neighbour distance (relative tolerance 10−6). A point tied with the 10th neighbour is therefore not a mistake. Duplicates count once, -1 ids are misses, and the function raises an error if the ties run past the end of the ground-truth list. Thirteen unit tests cover these cases, including integer-valued data with many ties. Ground truth is IndexFlatL2's top 120, with distances recomputed in float64 and re-sorted, so float32 BLAS rounding cannot reorder exact ties. Agreement with the stored neighbours: on SIFT, {{num:p1_sift_n_queries_differing}} of 10,000 queries have a top-10 id set different from the file's. All {{num:p1_sift_n_differing_only_by_ties}} differ only by points tied at the 10th distance (SIFT is integer-valued). On GloVe it is {{num:p1_glove_n_queries_differing}} query, also a tie. Tie-aware recall against the files is therefore {{num:p1_sift_recall_ours_vs_file_mean|.4f}} and {{num:p1_glove_recall_ours_vs_file_mean|.4f}}. A naive id-set recall would have marked those {{num:p1_sift_n_queries_differing}} SIFT queries as errors.

{{table:part1_exact}}

Why one query at a time is about {{num:p1_sift_batch_over_single|.0f}}× slower than a batch, even on one core. For a single query FAISS runs a SIMD scan. It streams the whole {{num:p2_sift_exact_size_mib|,.0f}} MiB matrix from RAM for every query and does only 2 flops per 4-byte float, so it is bound by memory bandwidth ({{num:p1_sift_single_gbps|.0f}} GB/s here). For a batch, FAISS uses a BLAS matrix multiply. Its cache-sized tiles let each block of base vectors be reused by many queries, so the work becomes compute-bound. The switch is a hard threshold at nq·d ≥ {{num:p1_blas_threshold|,}}: on one thread, {{num:p1_sift_batch_below_blas_threshold_nq}} SIFT queries in one call run at {{num:p1_sift_batch_below_blas_threshold_qps|.0f}} QPS and {{num:p1_sift_batch_above_blas_threshold_nq}} queries at {{num:p1_sift_batch_above_blas_threshold_qps|.0f}} QPS. Eight threads raise the speed-up only from {{num:p1_sift_batch_over_single|.0f}}× to {{num:p1_sift_batchmax_over_single|.0f}}×, because the four cores share one memory bus and one power budget.

Why IVF-PQ cannot reach high recall. IVF-PQ ranks candidates by distances approximated from 8-bit sub-quantizer codes. Raising nprobe only brings more candidates in. It cannot shrink the quantisation error, which is comparable to the small gaps between successive neighbour distances, so true neighbours are out-ranked by slightly farther impostors. The ceiling rises with code size (Table 4) but stays below 0.90 even with 2 dimensions per sub-vector. Exact re-ranking of a shortlist would remove the ceiling, but that is no longer plain IVF-PQ.

3. Experiment on the standard data: query difficulty on GloVe-100

Hypothesis (committed before running; hypothesis.md). At the setting that gives about 0.95 on average: (H1) the hardest quartile by relative contrast gets ≤ 0.85 and the easiest ≥ 0.99; (H2) the gap is largest for IVF-PQ, then IVF-Flat, then HNSW; (H3) the hardest bin needs ≥ 4× the search effort of the easiest; (H4) HNSW latency rises for hard queries while IVF-Flat latency stays flat. Method. RC = (exact mean distance from the query to all 1,183,514 base vectors) / (distance to its 10th neighbour). Bins are the tuning-half quartiles (edges {{num:p3_rc_edge1|.3f}}, {{num:p3_rc_edge2|.3f}}, {{num:p3_rc_edge3|.3f}}). Each index runs at its recall-0.95 setting from Table 2, and IVF-PQ at its highest-recall setting. GloVe is intrinsically hard: its median test RC is {{num:p3_glove_test_rc_median|.2f}}, against {{num:p3_sift_rc_median|.2f}} for SIFT.

Results. H1 is supported. HNSW falls from {{num:p3_hnsw_q4_recall|.3f}} (Q4) to {{num:p3_hnsw_q1_recall|.3f}} (Q1), and IVF-Flat from {{num:p3_ivfflat_q4_recall|.3f}} to {{num:p3_ivfflat_q1_recall|.3f}}. In Q1, {{num:p3_hnsw_q1_frac_below_08|x100.0f}}% of queries score below 0.8, against none in Q3–Q4. H3 is supported, strongly. Q2 already needs about 10× the efSearch of Q4 ({{num:p3_hnsw_need_q2}} vs {{num:p3_hnsw_need_q4}}), and Q1 does not reach 0.95 even at efSearch=1024 or nprobe=512. H2 is rejected. The Q4−Q1 gap is almost identical for all three indexes (about 0.16), and IVF-PQ is uniformly worse in every bin rather than disproportionately worse on hard queries. Difficulty is therefore a property of the query's neighbourhood, not of the index structure. With low RC, many points sit at nearly the 10th-neighbour distance, so any search that examines a bounded candidate set misses some of them. H4 is half-supported. HNSW latency rises from {{num:p3_hnsw_q4_lat_ms|.2f}} to {{num:p3_hnsw_q1_lat_ms|.2f}} ms (Spearman ρ(RC, latency) = {{num:p3_hnsw_spearman_lat|.2f}}): with many near-equal candidates its beam keeps improving and visits more nodes before it converges. IVF-Flat latency is not flat but slightly lower for hard queries ({{num:p3_ivfflat_q1_lat_ms|.2f}} vs {{num:p3_ivfflat_q4_lat_ms|.2f}} ms). A plausible reason, which we did not test, is that low-RC queries lie in sparse regions whose cells hold fewer vectors.

4. Experiment on our own data: distribution drift after training

Set-up (annbench/synth.py, seeded). The data are a 64-d mixture of 50 Gaussian clusters, each lying in its own random 8-d subspace. Each index is trained and built on 200K old vectors, then 200K new vectors are added, drawn from the same mixture shifted by δ·R along a fixed random direction (R = RMS radius of the old data). The 1000+1000 queries come from the shifted distribution, and ground truth is exact over all 400K vectors. Only δ changes: δ = 0 is the control, then 0.25, 0.5, 1 and 2, all from identical random draws. Indexes are HNSW (M=16), IVF-Flat (nlist=1024) and IVF-PQ (nlist=1024, 16 B/vector). On the control's tuning queries, each index's search parameter is fixed at the smallest value reaching recall 0.95. Where 0.95 is unreachable (IVF-PQ and, unexpectedly, the stale HNSW), it is the smallest value reaching 99% of that index's maximum: efSearch={{num:p4_fixed_hnsw}}, nprobe={{num:p4_fixed_ivfflat}} and nprobe={{num:p4_fixed_ivfpq}}. Stale indexes keep the quantizers trained on the old data; rebuilt indexes are trained on all 400K. Part 4 uses the median of 7 passes, because its passes are short.

What happened and why. IVF-PQ breaks in recall, as predicted (H2). Its recall falls from {{num:p4_ivfpq_stale_d0p0_recall|.3f}} to {{num:p4_ivfpq_stale_d2p0_recall|.3f}} at δ=2, and rebuilding restores {{num:p4_ivfpq_rebuilt_d2p0_recall|.3f}}. The codebooks were trained on small residuals around old centroids, but a new vector's residual is dominated by the shift, so its encoding error grows from {{num:p4_ivfpq_stale_d0p0_pq_rel_error|.2f}} to {{num:p4_ivfpq_stale_d2p0_pq_rel_error|.2f}}× the 10th-neighbour distance (roughly linear in δ, i.e. squared error ∝ δ2). The approximate distances then no longer rank neighbours. IVF-Flat breaks in cost, not recall (H1 partly supported). Recall stays at {{num:p4_ivfflat_stale_d2p0_recall|.3f}}, but the new vectors pile into the cells on the edge facing the shift. The largest list grows from {{num:p4_ivfflat_stale_d0p0_max_list_size|,}} to {{num:p4_ivfflat_stale_d2p0_max_list_size|,}} vectors (30×, as predicted). Queries in the new region therefore compute {{num:p4_ivfflat_stale_d2p0_dist|,.0f}} distances instead of {{num:p4_ivfflat_stale_d0p0_dist|,.0f}}, and QPS falls from {{num:p4_ivfflat_stale_d0p0_qps|,.0f}} to {{num:p4_ivfflat_stale_d2p0_qps|,.0f}}. The predicted slow-down of more than 5× did not happen. Only a few cells become huge (list-imbalance factor n·Σni2/(Σni)2 = {{num:p4_ivfflat_stale_d2p0_list_imbalance|.1f}}), and the other probed cells stay normal-sized. Rebuilding restores {{num:p4_ivfflat_rebuilt_d2p0_qps|,.0f}} QPS. HNSW is not hurt by drift (H3 supported). It has nothing trained, and its work stays at about {{num:p4_hnsw_stale_d2p0_dist|.0f}} distance computations per query at every δ. Recall at δ=2 is {{num:p4_hnsw_stale_d2p0_recall|.3f}}. IVF-PQ also slows ({{num:p4_ivfpq_stale_d0p0_qps|,.0f}} → {{num:p4_ivfpq_stale_d2p0_qps|,.0f}} QPS), for the same list-imbalance reason. A surprise contradicts H4. In the control, the stale HNSW reaches only {{num:p4_hnsw_stale_d0p0_recall|.3f}}, against {{num:p4_hnsw_rebuilt_d0p0_recall|.3f}} for the rebuilt one, so inserting the same vectors in two batches costs recall even with no drift. A post-hoc diagnostic (part4_hnsw_order.py, not pre-registered) shows three things. First, the loss is structural: the two-batch graph still reaches only {{num:p4o_two_batch_recall_ef1024|.3f}} at efSearch=1024, against {{num:p4o_one_pass_recall_ef1024|.3f}} for one pass. Second, it is not a race in parallel insertion: a single-threaded build gives {{num:p4o_two_batch_t1_recall_ef1024|.3f}}. Third, no node is unreachable. Instead the two batches are under-wired: only {{num:p4o_two_batch_old_to_new_pct|.0f}}% of the old nodes' base-layer edges point to new nodes (one pass: {{num:p4o_one_pass_old_to_new_pct|.0f}}%), and new nodes have median in-degree {{num:p4o_two_batch_indeg_new|.0f}} against {{num:p4o_two_batch_indeg_old|.0f}}. The old nodes chose their neighbours before the new data existed, and HNSW's diversity heuristic rarely replaces those links, so a greedy search that settles among one batch can miss neighbours in the other. Under drift, almost all true neighbours are new vectors wired among themselves, which is why the stale graph's recall rises with δ. The dip at δ=1 ({{num:p4_hnsw_stale_d1p0_recall|.3f}}) is probably the same effect where shifted clusters land next to other old clusters (not tested). Not tested: drift in the queries alone, rotations, or new clusters appearing; deletions; retraining only the PQ codebooks; other HNSW M/efConstruction values; data sizes other than 400K.

5. Answers

  1. Fastest at recall 0.95. HNSW, on both datasets: {{num:p2_sift_hnsw_95_qps|,.0f}} vs {{num:p2_sift_ivfflat_95_qps|,.0f}} QPS for IVF-Flat on SIFT, and {{num:p2_glove_hnsw_95_qps|,.0f}} vs {{num:p2_glove_ivfflat_95_qps|,.0f}} on GloVe. IVF-PQ never reaches 0.95. The winner does not change, but every index is 7–10× slower on GloVe. Why: HNSW's greedy graph walk reaches the neighbourhood after about {{num:p2_sift_hnsw_95_dist_comps|,.0f}} distance computations on SIFT, while IVF-Flat must scan entire lists ({{num:p2_sift_ivfflat_95_dist_comps|,.0f}}). GloVe's low relative contrast (median {{num:p3_glove_test_rc_median|.2f}} vs {{num:p3_sift_rc_median|.2f}}) means neighbours are barely closer than other points. Both indexes must then examine far more candidates ({{num:p2_glove_hnsw_95_dist_comps|,.0f}} and {{num:p2_glove_ivfflat_95_dist_comps|,.0f}}), and the advantage of following edges over scanning cells persists.
  2. Costs. HNSW needs no training, but it is the largest index: {{num:p2_sift_hnsw_bpv|.0f}} B/vector on SIFT, the 512 B vector plus up to 2M neighbour links. It took {{num:p2_sift_hnsw_build_s|.0f}} s to build on SIFT and {{num:p2_glove_hnsw_build_s|.0f}} s on GloVe. IVF-Flat stores the raw vectors plus ids ({{num:p2_sift_ivfflat_bpv|.0f}} B/vector), and its build time is mostly k-means. PQ saves memory: {{num:p2_sift_ivfpq_bpv|.0f}} B/vector, 7× smaller than IVF-Flat. But it pays a large precomputed table in RAM ({{num:p2_sift_ivfpq_extra_ram_mib|.0f}} MiB at nlist=4096, m=64, more than its codes), the slowest build (k-means plus PQ training) and, above all, accuracy: lossy distances cap recall at {{num:p2_sift_ivfpq_m64_maxrecall|.3f}} (SIFT) and {{num:p2_glove_ivfpq_m50_maxrecall|.3f}} (GloVe).
  3. What Parts 3 and 4 imply. A headline "recall 0.95" is an average over an in-distribution query set on a freshly built index. Part 3 shows the average hides a tail: a quarter of the hardest GloVe queries score below 0.8, so a workload with harder queries than the benchmark will see lower recall at the same setting. Part 4 shows the headline also assumes a static index. After drift, a trained index degrades silently: IVF-PQ loses recall ({{num:p4_ivfpq_stale_d0p0_recall|.2f}} → {{num:p4_ivfpq_stale_d2p0_recall|.2f}}), and IVF-Flat keeps recall but slows down ({{num:p4_ivfflat_stale_d0p0_qps|,.0f}} → {{num:p4_ivfflat_stale_d2p0_qps|,.0f}} QPS). HNSW's quality even depended on insertion order. Settings tuned once on a fresh index, with average recall on benchmark queries, can therefore overstate quality in production.
  4. 150K vectors or 10M; 100 ms per query; 16 GB RAM. Brute force is linear in n. Our single-query timings ({{num:p1_sift_single_ms|.0f}} ms at 1M SIFT, {{num:p1_glove_single_ms|.0f}} ms at 1.18M GloVe) extrapolate to {{num:p1_sift_ms_150k|.0f}} ms and {{num:p1_glove_ms_150k|.0f}} ms at 150K. For 150K: no ANN. Exact search is about 12× inside the budget with perfect recall, no build and no tuning, and uses at most 73 MiB of vectors. Only if throughput mattered (more than about 100 QPS per core) would we add HNSW (M=16). For 10M: ANN is required. Exact search would take about {{num:p1_sift_ms_10m|.0f}} ms (SIFT-like) or {{num:p1_glove_ms_10m|.0f}} ms (GloVe-like) per query, beyond 100 ms, and a single query cannot use BLAS batching. We would use HNSW, M=16–32, efConstruction=200, with efSearch re-tuned on held-out queries for the target recall. The 1M results suggest efSearch ≈ 50–100 for SIFT-like data and 400–800 for GloVe-like data, which means well under 10 ms per query at 10M, since graph search cost grows slowly with n. Memory: {{num:p2_sift_hnsw_M16efC200_bpv|.0f}}–{{num:p2_sift_hnsw_bpv|.0f}} B/vector gives about {{num:p2_sift_hnsw_gib_10m|.1f}} GiB at M=32 for SIFT-like vectors, which fits in 16 GB. The build takes tens of minutes on 8 threads. If data drifts or arrives in batches, Part 4 says to rebuild periodically. IVF-PQ is only worth it when RAM, not latency, is the constraint, and then with exact re-ranking.
  5. Ways our benchmark could mislead. (a) Laptop timing noise. CPU speed drifted by {{num:cal_spread_pct|.0f}}% between scripts, and one short Part 4 measurement was corrupted by a transient: it showed 8× slower, while in isolation it was 2.4×. Tested: calibration rows, page-fault counts, the AC guard and 7 repeats in Part 4 bound the noise. Ratios under about 1.3× measured at different times should not be trusted, but the conclusions above rest on ratios of 2.6× or more. (b) Single-thread, single-query timing in Python. This measures the latency regime. With batching, exact search gains {{num:p1_sift_batch_over_single|.0f}}× from BLAS, and IVF can batch its coarse search, so throughput rankings may differ. Also, this Windows FAISS wheel ships only generic (non-AVX2) kernels, which may penalise scan-heavy IVF-Flat more than HNSW. Only partly tested: batching only for exact search, and harness overhead ({{num:call_overhead_us|.1f}} µs per call) measured. Untested: other builds and libraries (e.g. hnswlib), and repeated builds (HNSW's multi-threaded build is not deterministic).
