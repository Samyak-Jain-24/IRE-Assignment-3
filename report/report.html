Protocol. GloVe vectors and queries are L2-normalised, so Euclidean distance ranks exactly like angular distance, and every index uses L2. Queries 0–4999 (tuning half) are used for every choice: where a parameter sweep stops, which configurations form the trade-off curve, and which setting is used for recall 0.90/0.95. All reported recall and speed numbers come from queries 5000–9999 (test half). Speed is measured one query per search() call on a single thread. FAISS's OpenMP threads and its bundled OpenBLAS pthreads, which ignore omp_set_num_threads, are both pinned to one thread with threadpoolctl. Each speed number is the median of 3 full passes over the 5000 test queries, each after a warm-up. Builds use all 8 hardware threads. The harness costs {{num:call_overhead_us|.1f}} µs per call (timed on a 1-vector index). That is under 5% of any configuration reported below.

1. Exact baseline

recall@10. Our function counts a returned id as correct if its true distance is no larger than the distance of the true 10th neighbour (relative tolerance 10−6). Any point tied with the 10th neighbour is therefore accepted. Duplicates count once and -1 ids are misses. It raises an error if the ties run past the end of the ground-truth list. Thirteen unit tests cover ties, tolerance, duplicates, padding and an integer-valued data set with many ties. Ground truth is FAISS IndexFlatL2's top 120, with distances recomputed in float64 and re-sorted, so that BLAS rounding cannot reorder exact ties. Agreement with the files: on SIFT, {{num:p1_sift_n_queries_differing}} of 10,000 queries have a different top-10 id set from the stored one. All {{num:p1_sift_n_differing_only_by_ties}} of them differ only by points tied at the 10th distance (SIFT is integer-valued). On GloVe it is {{num:p1_glove_n_queries_differing}} query, also a tie. Tie-aware recall of our exact results against the stored lists is {{num:p1_sift_recall_ours_vs_file_mean|.4f}} (SIFT) and {{num:p1_glove_recall_ours_vs_file_mean|.4f}} (GloVe). Without the tie rule, the {{num:p1_sift_n_queries_differing}} SIFT queries would wrongly score below 1.

Why batching is about {{num:p1_sift_batch_over_single|.0f}}× faster on one core. One query at a time, FAISS runs a SIMD scan. Every query streams the whole {{num:p2_sift_exact_size_mib|,.0f}} MiB matrix from RAM and does only 2 flops per float loaded, so it is limited by memory bandwidth: {{num:p1_sift_single_ms|.0f}} ms per SIFT query is about 13 GB/s. With many queries, FAISS switches to a BLAS matrix multiply. The multiply works on tiles small enough to stay in cache, so each block of base vectors is loaded once and reused for many queries, and the work becomes compute-bound (AVX-512 FMA). The switch happens exactly at nq·d ≥ {{num:p1_blas_threshold|,}}: on one thread, a SIFT batch of {{num:p1_sift_batch_below_blas_threshold_nq}} queries runs at {{num:p1_sift_batch_below_blas_threshold_qps|.0f}} QPS and a batch of {{num:p1_sift_batch_above_blas_threshold_nq}} at {{num:p1_sift_batch_above_blas_threshold_qps|.0f}} QPS. Same work per query, different algorithm. Eight threads add comparatively little, because the 4 cores share one memory bus and one power budget.

Why IVF-PQ cannot reach 0.95. IVF-PQ ranks candidates by approximate distances computed from 8-bit sub-quantizer codes. Raising nprobe only brings more candidates into play. It cannot reduce the quantisation error, which is not small compared with the gaps between successive neighbour distances, so true neighbours keep being out-ranked by impostors that are only slightly farther away. The ceiling therefore rises with code size (Table 4) but stays below 0.95 even at 2 dimensions per sub-vector. Re-ranking the shortlist with exact distances would fix this, but that is not plain IVF-PQ.

3. Experiment on the standard data: query difficulty on GloVe-100

Hypothesis (committed before running, see hypothesis.md). At the setting that gives about 0.95 on average, the hardest quartile of queries by relative contrast will get ≤ 0.85 and the easiest ≥ 0.99. IVF-PQ will show the largest gap between bins, then IVF-Flat, then HNSW. The hardest bin will need at least 4× the search effort of the easiest. HNSW latency will rise in hard bins, while IVF-Flat latency stays flat. Method. RC = (mean distance from the query to all 1,183,514 base vectors, computed exactly) / (distance to its 10th neighbour).
